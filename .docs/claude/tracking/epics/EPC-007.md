# EPC-007 — Multi-agent orchestrator

**Status:** Phase 1 Done
**Roadmap:** [Roadmap](../ROADMAP.md)
**ADR:** [ADR-007](../../architecture/adrs/ADR-007-multi-agent-orchestrator.md)

## Outcome

An orchestrator agent the IDE spawns as a subagent with its own context window.
It splits work along real seams, proposes a delegation plan for approval, puts
workers on the parts in parallel, and accounts for every result — including the
failures.

## Guards against unbounded delegation

The failure this epic is most exposed to is an agent that keeps delegating.
Four constraints hold the line, and each names the failure it prevents:

Two of these are enforced by the editor because the exported `tools:` line
restricts what the agent can reach. The rest are prose the agent is asked to
follow — real, but a different kind of guarantee, and worth not confusing.

| Guard | Enforced by | Failure prevented |
|---|---|---|
| Orchestrator exports without Edit/Write/Bash | Editor | Implementing instead of delegating |
| Developer exports without Agent | Editor | Unbounded delegation tree |
| Every worker prompt says not to spawn | Instruction | Depth overrun, which fails silently |
| Re-delegate at most twice, then escalate | Instruction | Infinite retry on a mis-specified task |
| Report every outcome | Instruction | Synthesised results for work that never ran |

The distinction was not free — see [FND-028](../findings/FND-028.md). The first
two rows were prose too until the export was read rather than assumed.

## Grilling record

Interrogated 2026-08-08, 10 questions, all recommendations confirmed by the user.
Settled: rule and agent coexist; orchestrator stays `kind: agent`; two levels
only; dynamic skills are prompt composition rather than new API; approval gate
before spawning; the server stays stateless; token governance belongs to the
editor.
