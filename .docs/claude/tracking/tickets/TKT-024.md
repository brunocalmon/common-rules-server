# TKT-024 — Orchestrator agent definition

**Type:** Feature
**Status:** Done
**Epic:** [EPC-007](../epics/EPC-007.md)

Add the meta-agent that splits work, spawns workers, and accounts for results.
Distinct from the orchestrator *rule*, which routes a single agent.

## Acceptance criteria

- [x] `resources/agents/orchestrator.md` exists and parses
- [x] No `edit` or `execute` in its tools — it cannot do the work itself
- [x] Approval gate before spawning stated as a constraint, not a suggestion
- [x] One flat level of workers; every worker told not to spawn
- [x] Re-delegation bounded at two attempts, then escalate
- [x] Failures reported, never absorbed
- [x] `comes-from` edge back to the orchestrator rule

## Why

The user's question — "a regra orquestrador consegue orquestrar os agents? Eu
acho que não, pq é só uma regra certo?" — was correct. A rule is text the IDE
agent reads; it cannot spawn anything. Parallelism needs an agent.

Four of the constraints exist specifically to stop unbounded delegation:

| Constraint | Failure it prevents |
|---|---|
| No `edit`/`execute` | Orchestrator quietly implementing instead of delegating |
| One flat level | Depth overruns that fail silently on Claude Code (cap: 3) |
| Two re-delegations max | Infinite retry on a mis-specified task |
| Report every outcome | Synthesised results for work that never ran |
